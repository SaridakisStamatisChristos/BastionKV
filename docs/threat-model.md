# Trust boundaries

Untrusted file bytes, accidental corruption and bounded malicious framing are parsed defensively. Fixed metadata size; validated limit caps; checked frame and record ranges; header/payload checksums; exact markers; strict ordering/sequence; generated paths; regular-file checks; no Rust unsafe; no third-party Rust dependencies. Fault env variables have no effect in ordinary builds.

Trusted: OS, filesystem fsync/rename/lock semantics, hardware, directory owner, and cooperating processes. Advisory locks prevent accidental independent opens, not malicious writes. A directory owner able to race symlink replacement or rewrite a checksummed manifest can forge/rollback a valid database; CRC is not a MAC. No encryption, access accounts, network protocol, directory-race sandbox, or forensic rollback detection is claimed. Use restrictive filesystem permissions and trusted directory ancestors. Keys/values may hold secrets: CLI/debug dumps and filesystem access require the application's permission policy.

`verify` is offline, refuses an active writable lock, and is read-only. Writer open performs documented cleanup/truncation. Arbitrary length fields cannot request more than absolute validated frame limits. Logical state and 128 active snapshots bound data retention, but allocator overhead, copy-on-write maps and snapshot multiplication mean this is not a strict process memory cap.

Format library errors preserve corruption locations and I/O sources; expected errors don't panic. Poisoning prevents transactions after uncertain I/O. No automatic deletion of non-format files. CI tests actual implementation and builds both fault-enabled and default binaries. Supply chain: standard library/toolchain only in Rust package; Python harness uses standard library SQLite. Cargo audit has no third-party package surface; compiler/OS/action vulnerabilities remain external dependencies. No security certification or production assurance beyond the observed target is claimed.
